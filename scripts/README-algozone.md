# Algozone dashboard — how it works

The performance board and return calculator on `/pages/algozone.html` are
driven by one static file:

    data/algo-stats.json

It is generated by the CFA Structure Engine (the `Trading algo` repo), not by
this site. The page fetches it at load time, so refreshing the numbers is a
data commit — no HTML change needed.

## Refreshing the numbers

In the `Trading algo` repo, on the Mac:

    bash algozone.sh ~/Developer/v6        # 750 sessions = 3 years (default)
    bash algozone.sh ~/Developer/v6 0      # the WHOLE archive, 2015 -> today

That writes `output/public_stats.json` and copies it here as
`data/algo-stats.json`. Then commit and push this repo.

**Window matters, and a short one flatters.** Going from 250 to 750 sessions
moved v2 from +0.336 to +0.286 R/trade signal-pure, and +0.139 to +0.092 after
costs. The shipped file is 3 years because that is what fits a sandbox
execution limit; `--days 0` on the Mac scores ~2,833 sessions per stock and is
the better number to publish. NIFTY is the exception — its futures archive is
only ~69 sessions deep, so NIFTY option counts stay small no matter what.

## Testing after a change

    npm install jsdom --no-save
    node scripts/test-algozone.js . data/algo-stats.json

93 checks: it renders the real page against the real data in jsdom, drives
every control, and independently re-derives the calculator's arithmetic from
the JSON. All must pass before deploying.

## Three rules the page enforces on itself

1. **Signal-pure is never shown alone.** The board defaults to signal-pure and
   the calculator always prints the after-costs figure beside it. This now
   applies to options too: `data/algo-stats.json` carries
   `options[model][pure|honest][instrument]`, the honest book adding 2% of
   premium per round trip for brokerage, STT and one tick of spread.
2. **Option positions are sized as a fraction of capital** (25% by default), not
   "as many lots as the money buys". The 100% setting exists but says what it
   costs you when the stop hits.
3. **Compounding walks the real path.** `algo-stats.json` carries
   `dates`, `coverage` and `paths[model][mode][equity|options][instrument]` —
   the actual per-session return sequence. Monthly and daily reinvestment
   compound that sequence, carrying each period's closing capital into the
   next, so losing months are included and the volatility drag a
   constant-rate model hides is not. "Worst" and "Best" in the projection
   table are the real worst/best month and twelve-month stretch in the data,
   not a symmetric error bar. `coverage` clips each instrument to the window
   its archive actually spans — without it, months predating an archive count
   as flat zero-return months and hide every real loss.
4. **Risk of ruin is modelled, not implied.** Every other figure is an
   average, and averages assume the account survives to collect them. The
   calculator walks a run of consecutive stop-losses using the chosen sizing,
   re-sizing after each loss, and compares it with the longest losing streak
   the model actually produced. If that run ends the account the panel turns
   red and explicitly disowns the annual figure above it. Example: MARUTI
   options, ₹10,000, 100% deployed — dead after 2 stops, against a 6-loss
   streak in the data.
5. **Compounding switches itself off above ~20% a month.** Twelve powers of a
   thin, high-percentage option result produces figures with no physical
   meaning (₹1 lakh "becoming" ₹1,980 crore). Above the ceiling the annual row
   falls back to twelve flat months and explains why.

## Shape of `data/algo-stats.json`

Everything is keyed by **model → scoring mode → trailing window**:

    models[v2].equity.honest["3M"].overall
    models[v2].equity.honest["3M"].per_instrument["MARUTI"]
    models[v2].futures.honest["3M"]
    options[v2].honest["3M"]["MARUTI"]
    paths[v2].honest.equity["MARUTI"]      # window-independent, indexed into dates[]

Windows are `1M / 3M / 6M / 1Y / All`, measured back from the newest session,
matching `backtest_range._periods` so the public board and the internal hub
agree on what "last 3M" means. The page's Period control switches between them.

## The four market views

`Stocks` (cash equity) · `Stock Options` (15 names, index excluded) ·
`NIFTY Options` (index only) · `NIFTY Futures`. All four appear on **both** the
board and the calculator.

Sizing differs by view and the calculator hides the controls that do not apply:
stocks split capital across N concurrent slots; options buy premium up to a
chosen deployment %; **futures are sized in whole lots against margin**, so
neither the deployment % nor the instrument dropdown is shown. Futures also use
their own rupees-per-lot path (`paths[model][mode].futures`) rather than the
equity % path — margin, not notional, is the capital at risk.

The futures tab exists because it was asked for and because the option numbers
are derived from the same signals — but it carries a standing caution in the
board note: futures losses are not capped at the margin posted, and one lot
needs ~₹1.65L. It is not a recommendation.

## We read the NIFTY futures chart; we do not trade futures

NIFTY structure is detected on the futures series because it is the cleanest
continuous intraday series for the index. The trade booked against it is a
bought ATM CE/PE. There is no futures trading view on the page — the ₹/lot
futures numbers still exist in `algo-stats.json` for internal reference only.

## The one thing not to change casually

The board defaults to **signal-pure** backtest numbers, and the calculator
always shows the **after-costs** figure beside them. That pairing is
deliberate: signal-pure scoring excludes trades still open at 15:30 and
applies no brokerage, so it runs roughly 2–3x the tradeable number. Removing
the after-costs row would leave visitors sizing real money off the optimistic
one.
